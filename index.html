NETWORK ENGINEERING LAB

Multi-Domain Constraint-Based SR-MPLS Traffic Engineering

Exploring how a centralized SDN/PCE controller can perform constraint-based traffic engineering across multiple independent SR-MPLS domains interconnected by BGP-LU.
SR-MPLS · BGP-LS · BGP-LU · OpenDaylight · PCEP · CSPF · SAMCRA

Project Objective

Large backbone networks are not always built as one single IGP domain. They may consist of multiple independent regional networks, each operating its own IGP and Segment Routing control plane.

The objective of this lab is to investigate whether a centralized SDN/PCE controller can obtain a global traffic-engineering view of these independent domains and calculate an end-to-end path according to multiple constraints.

The experiment focuses specifically on Multi-Domain Constraint-Based SR-MPLS Traffic Engineering rather than building one large global SR-MPLS IGP domain.

Lab Architecture

The lab represents four independent regional SR-MPLS domains: Australia, Singapore, Japan and Hong Kong. Each region maintains its own IGP/SR topology. Inter-domain transport is provided using BGP Label Unicast.

Control-Plane Components

SR-MPLS

Provides label-based forwarding and Segment Routing inside each independent regional IGP domain.

BGP-LS

Exports topology and traffic-engineering information toward the centralized controller.

BGP-LU

Provides labelled reachability between otherwise independent SR-MPLS domains.

OpenDaylight

Maintains the global Traffic Engineering Database and performs centralized path computation.

CSPF / SAMCRA

Computes paths according to topology and traffic-engineering constraints rather than simple shortest-path reachability.

PCEP

Provides the southbound mechanism used to program the computed traffic-engineered path toward the network.

The Multi-Domain Problem

BGP-LS provides visibility into the individual regional topologies, but independent domains do not automatically appear as one continuous SR topology.

The controller therefore needs an abstraction for the inter-domain BGP-LU connections so that the global path computation engine can evaluate both native intra-domain links and WAN transitions.

Native SR Domain ↓ BGP-LU Transition ↓ Native SR Domain ↓ BGP-LU Transition ↓ Native SR Domain

These WAN transitions are treated as inter-domain forwarding edges, not as artificial SR Adj-SIDs.

Traffic Engineering Metrics

The global Traffic Engineering Database was enriched with operational link metrics so that path selection could be evaluated against more than a simple IGP cost.

Delay

Link latency can be used as an end-to-end path constraint.

Jitter

Delay variation is collected as an additional operational metric.

Packet Loss

Loss information can be included in multi-constraint path evaluation.

Bandwidth

Maximum, utilized and available bandwidth can be represented in the traffic-engineering database.

TE Metric

Traffic-engineering cost can be manipulated independently from normal IGP forwarding decisions.

Global Path Computation

The controller first computes the path from a global IPv4 traffic-engineering view. This allows the path engine to traverse both native BGP-LS topology edges and the inter-domain BGP-LU transitions.

The selected end-to-end path is then decomposed according to domain boundaries.

Global Constraint-Based Path ↓ AU Native SR Segment ↓ AU → SG BGP-LU Transition ↓ SG Native SR Segment ↓ SG → HK BGP-LU Transition ↓ HK Native SR Segment

Multi-Domain Path Demonstration

During testing, path metrics were deliberately modified to make a direct AU-to-HK path unsuitable for the configured constraints.

The path computation engine selected a transit path through the Singapore domain instead.

AU-PE | | SR-MPLS v AU-PBR02 | | BGP-LU v SG-PBR02 | | Native SG SR-MPLS v SG-PBR01 | | BGP-LU v HK-PBR01 | | Native HK SR-MPLS v HK-PBR02 | v HK-PE

This demonstrates that the controller's path computation is not restricted to selecting a direct inter-domain link. A third regional SR-MPLS domain can participate as a transit domain when required by the traffic-engineering decision.

Path Decomposition

A key part of the experiment is separating global path computation from domain-specific forwarding instructions.

A global path may contain a sequence conceptually similar to:

SR Segment → BGP-LU Label → SR Segment → BGP-LU Label → SR Segment

Native links retain their SR semantics, while BGP-LU transitions retain their BGP label semantics. The controller does not attempt to represent BGP-LU WAN links as fake SR Adj-SIDs.

PCEP Programming

After path computation, PCEP was used to validate controller-driven SR-MPLS LSP programming toward Junos PCCs.

Control-Plane Validation

The programmed LSP was reported by the router as:

  • Path Setup Type: spring-te
  • State: Up
  • Active Path: Yes
  • Controller: ODL
  • Path CSPF Status: external_cspf

The received PCE ERO and the ERO reported by the router matched, providing control-plane confirmation that the path was accepted.

Data-Plane Validation

Successful PCEP programming alone does not prove that the forwarding path actually works. The final stage of the experiment therefore validated the path using real traffic.

20 packets transmitted 20 packets received 0% packet loss MPLS forwarding observed using traceroute.

The test confirmed end-to-end reachability across independent SR-MPLS domains using the controller-programmed traffic-engineered path.

Key Architectural Finding

Topology Visibility ≠ Forwarding Reachability

One of the most important findings from the lab is that having a global topology view does not automatically create global SR forwarding reachability.

BGP-LS can provide the controller with topology and SID knowledge, but independent IGP domains still maintain independent forwarding state. A remote Node-SID learned by the controller does not automatically become a usable end-to-end label inside every other SR domain.

BGP-LU therefore performs an important role in the current architecture: it provides labelled reachability across the boundaries between independent SR-MPLS domains.

What This Lab Demonstrates

  • A centralized controller can build a traffic-engineering view across multiple independent SR-MPLS domains.
  • Constraint-based path computation can operate across both native intra-domain topology and inter-domain WAN transitions.
  • The computed global path can be decomposed into domain-specific SR-MPLS segments and BGP-LU transitions.
  • A regional SR domain can be selected as a transit domain when the constraint-based path requires it.
  • PCEP can be used to translate the controller decision into an operational SR-MPLS LSP.
  • Control-plane state and real data-plane forwarding can be validated independently.

Future Direction

The next architectural question is whether a purpose-built multi-domain SR controller could provide a more native abstraction than the current combination of independent SR domains and BGP-LU.

Such a controller could potentially maintain a global topology and SID database, perform constraint-based path computation, compile domain-specific forwarding instructions and program routers using interfaces such as PCEP, NETCONF or gNMI.

The long-term objective would be to investigate how globally coordinated SR-MPLS forwarding could operate across independent IGP domains without requiring those domains to become one single global IGP.

Conclusion

This experiment transformed multiple isolated SR-MPLS domains into a single traffic-engineering view from the perspective of the controller.

An end-to-end constrained path could be computed across regional boundaries, decomposed into SR-MPLS and BGP-LU forwarding components, programmed through PCEP and validated in the data plane.

The project is an exploration of Multi-Domain Constraint-Based SR-MPLS Traffic Engineering — not an attempt to merge independent regional networks into one IGP domain.
