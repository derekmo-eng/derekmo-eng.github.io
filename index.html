Multi-Domain Constraint-Based
SR-MPLS Traffic Engineering

Author: Derek Mo — CCIE #17538 + JNCIE-SP #2120  ·  Date: 6 October 2026

A practical demonstration of how a centralized SDN/PCE controller can perform constraint-based traffic engineering across multiple independent SR-MPLS domains interconnected by BGP-LU.

Test Objective

This lab demonstrates how OpenDaylight can build a global traffic-engineering view and compute constrained end-to-end paths across multiple independent SR-MPLS domains. The goal is not to collapse every region into a single IGP domain, but to preserve regional autonomy while still enabling end-to-end traffic engineering.

Regional Architecture

The environment contains four independent regional SR-MPLS domains: Australia, Singapore, Japan and Hong Kong. Each region has its own IS-IS/SR-MPLS control plane, with Provider Edge (PE) routers and Provider Border Routers (PBRs).

Inter-Domain WAN

The regions are interconnected through BGP Label Unicast (BGP-LU) links between the PBRs. The validated lab contains 10 physical WAN links represented as 20 directional topology edges. Australia and Japan have no direct WAN connection.

Global Traffic Engineering

BGP-LS exports the regional topology and Segment Routing information into OpenDaylight. ODL uses that information to build the base global Traffic Engineering Database (TED), allowing SPF, CSPF and SAMCRA to evaluate end-to-end paths across regional boundaries.

Path Programming

The selected global path is translated into domain-specific SR-MPLS forwarding instructions and the required BGP-LU transition. The orchestration layer resolves the destination-specific BGP-LU forwarding state, translates the outgoing label into the local/incoming label that the ingress PE must push, and programs both directions through PCEP as one logical transaction.

End-to-End Control Workflow

BGP-LS provides the regional topology and SR information that forms the base global TED. The collectors then enrich those existing links with live operational data such as delay, jitter, loss, bandwidth and BGP-LU forwarding state. CSPF or SAMCRA computes the constrained end-to-end path, which is then decomposed into native per-domain SR segments and BGP-LU transitions. The orchestration layer compiles the selected path and uses ODL PCEP to program the resulting bidirectional LSP pair.

BGP-LS → Global TED → Constraints → CSPF / SAMCRA → Path Decomposition → SR-MPLS + BGP-LU Label Translation → Bidirectional PCEP

How the Global TED Is Built

The information in the ODL metric table comes from two different sources. BGP-LS gives ODL the network graph and Segment Routing attributes, while the collectors add live operational data from the routers. This separation is important: the collectors do not invent the IS-IS links. They enrich links that ODL has already learned through BGP-LS.

1. IS-IS and SR Topology

The routers run their normal regional IS-IS/SR-MPLS control planes. BGP-LS exports the resulting topology and SR attributes to OpenDaylight.

ODL learns: nodes, directional IS-IS links, IGP/TE metrics, Prefix/Node SIDs and adjacency-SID information.

2. Collector Uses the BGP-LS-Derived Graph

The collector reads the graph that ODL built from BGP-LS and uses it as the base inventory. Local and remote addresses, router identity and edge direction are used to correlate each measurement with the correct ODL edge.

Important: native IS-IS links already exist before telemetry enrichment begins.

3. NETCONF and RPM Enrichment

The collectors connect to the Juniper routers over NETCONF. Junos RPM provides delay, jitter and packet-loss measurements, while interface data provides capacity and current traffic levels.

Derived values: delay, jitter, loss, maximum bandwidth, utilization and available bandwidth.

4. BGP-LU Forwarding State

NETCONF is also used to read MPLS/BGP-LU forwarding state from the PBRs. The collector records local/incoming-to-outgoing label mappings on the matching WAN edge.

Example: 321 → 51 means label 321 is local to the ingress side and is swapped to label 51 toward the WAN.

IS-IS / SR-MPLS → BGP-LS → ODL Base Graph + NETCONF / RPM Telemetry → Enriched Global TED → CSPF / SAMCRA

Where Each Field Comes From

BGP-LS: topology, IS-IS links, IGP/TE metrics and SR SID information.

NETCONF + RPM: delay, jitter and packet loss.

NETCONF interface statistics: link capacity and utilization; available bandwidth is derived from those values.

NETCONF MPLS state: BGP-LU incoming-to-outgoing label mappings.

Why This Matters

ODL therefore sees more than connectivity. It has a global topology plus live operating conditions and forwarding state. That allows the path-computation engine to make decisions using the current state of the network rather than only static IGP cost.

The measurements are directional, so AU → SG and SG → AU can have different delay, loss, bandwidth or label state and can be evaluated independently.

Key Architectural Point

Topology visibility and forwarding reachability are separate problems. BGP-LS gives the controller a global view of the network, but independent IGP domains still need an inter-domain forwarding mechanism such as BGP-LU. This experiment brings those two pieces together in one constraint-based TE workflow.

Engineering Note — LSP Traffic Counters

In the Junos operational outputs checked during this lab, we did not observe a directly usable per-LSP packet or byte counter for the externally provisioned SPRING-TE LSP. This is a statement about the commands and software behaviour observed in this test, not a claim that such counters can never exist in other Junos releases, platforms or telemetry paths.

For that reason, data-plane proof is built from several independent forwarding indicators rather than from a single LSP statistics counter: the installed SPRING-TE forwarding entry, the MPLS labels observed in traceroute, and successful CE-to-CE EVPN service traffic.

If a traffic-volume delta is required, packet and byte counters on the selected WAN interface can also be sampled before and after a test flow. This provides a practical way to confirm that traffic has moved onto the selected physical path even when the LSP object itself does not expose traffic statistics.

Constraint-Driven Bidirectional Path Re-Optimization

To demonstrate path re-calculation under a controlled lab condition, the WAN latency values were deliberately changed so that the previously preferred PBR01 path became less attractive and the PBR02 path became the lower-latency candidate. After the updated telemetry was reflected in ODL, the orchestrator was run again with the same SAMCRA constraints. ODL then re-computed the constrained path and selected the PBR02 pair.

This is an explicit re-provisioning demonstration: the latency change was intentionally introduced in the lab, the orchestrator was re-run, and the resulting bidirectional LSPs were programmed through PCEP. It is not presented as an autonomous continuous closed-loop controller.

A controlled latency change reversed the preference between the two AU↔SG border-router pairs. The orchestrator was then run again, SAMCRA selected the lower-latency PBR02 path, the forwarding compiler derived the new SR and BGP-LU ingress labels, and both directions were re-provisioned through PCEP.

Challenges Encountered and Lessons Learned

The most important engineering lesson from the lab was that global topology visibility, path computation and forwarding reachability are different problems. BGP-LS gave ODL a global topology view, but remote SR information alone did not make every SID directly reachable across independent IGP domains.

The BGP-LU stitched design therefore required an additional forwarding-compilation step. The orchestrator had to correlate the selected WAN transition with destination-specific BGP-LU state, translate the remote/outgoing label into the local/incoming label required at the ingress, and then build the PCEP ERO. This is why a value such as 321 is programmed at the head-end even though the corresponding downstream BGP-LU label may be 51.

Another lesson was that path-computation metadata and forwarding-programming metadata are not always the same thing. ODL may report an edge-level backup Adj-SID such as 16, while the PCEP compiler represents that regional part of the path with the selected PBR Node-SID such as 16101. These are different SR semantics, not conflicting values.

Bidirectional services also need to be treated as one logical operation. Forward and reverse paths are calculated independently because telemetry and forwarding state are directional, but the orchestrator programs them only after both directions pass pre-check. If the second direction fails during programming, the first direction is rolled back.

Why a Dedicated WAN IS-IS / SR-MPLS Domain Would Be Cleaner

The current BGP-LU stitched design is operationally valid and proves true end-to-end service forwarding across independent regional SR-MPLS domains. However, a dedicated WAN IS-IS / SR-MPLS domain would provide a cleaner native SR model because the WAN itself would advertise SR-aware topology, metrics, Node-SIDs and Adj-SIDs.

That would reduce the need for BGP-LU label translation and allow the path to be expressed more directly as regional SR → WAN SR → regional SR. It would also provide a clearer end-to-end SR representation and align the topology model more closely with the forwarding model.

A further advantage is that SR-TE path computation does not have to depend on a centralized controller. If the head-end router has sufficient SR topology and TE information, it can compute an SR-TE path itself. In that architecture, ODL/PCE remains valuable for global optimization, telemetry aggregation, policy and multi-domain orchestration, but it is not the only place where basic SR-TE path selection can occur.

Summary: BGP-LU stitching solves inter-domain reachability, while a dedicated WAN IS-IS / SR-MPLS design provides cleaner native SR programmability and can also enable head-end SR-TE computation when sufficient topology and TE information are available.

7. Current Demo Scope

For this demonstration, path changes are re-provisioned explicitly rather than by a persistent daemon updating an existing LSP in place. This keeps the workflow deterministic while still proving the full decision and programming chain: telemetry change → constrained recomputation → alternate path → new label compilation → bidirectional PCEP provisioning → live service validation.

The current PCEP compiler demonstration validates paths containing exactly one inter-domain BGP-LU transition. Wider multi-transition forwarding compilation remains an extension point.
