Multi-Domain Constraint-Based SR-MPLS Traffic Engineering

OpenDaylight · BGP-LS · BGP-LU · CSPF · SAMCRA · PCEP

Exploring how a centralized SDN/PCE controller can perform constraint-based traffic engineering across multiple independent SR-MPLS domains interconnected by BGP-LU.

Project Goal

The objective of this lab is to investigate how OpenDaylight can provide a global traffic-engineering view across multiple independent SR-MPLS domains while preserving separate regional IGP control planes.

Independent Domains

Australia, Singapore, Japan and Hong Kong operate as independent IS-IS / SR-MPLS domains.

Global Topology

BGP-LS exports topology and traffic-engineering information to OpenDaylight, allowing the controller to construct a global Traffic Engineering Database.

Constraint-Based TE

SPF, CSPF and SAMCRA can evaluate paths using topology and TE constraints such as metric, delay, loss and bandwidth.

Controller Programming

Selected forwarding instructions can be translated into SR-MPLS and BGP-LU forwarding information and delivered through PCEP.

Architecture

The regional networks remain separate SR-MPLS control-plane domains. The controller provides the global TE view rather than merging the regional IGPs into a single routing domain.

                 Independent IGP / SR-MPLS Control Planes
Key architectural principle: The design does not create one global IS-IS domain. Each region remains operationally independent while the SDN/PCE layer maintains the global TE view.

Actual Lab Topology

The test environment contains four regional SR-MPLS domains: Australia, Singapore, Japan and Hong Kong. Each region contains PE and PBR functions with inter-domain connectivity between the regional border routers.

Actual EVE-NG lab topology used for the multi-domain SR-MPLS traffic-engineering experiment.

How Multi-Domain Traffic Engineering Works

1

Regional SR-MPLS Domains

Each region runs its own IS-IS and SR-MPLS control plane independently.

2

BGP-LS Topology Collection

Regional topology, SR and TE information is exported toward OpenDaylight using BGP-LS.

3

Global Traffic Engineering Database

OpenDaylight builds a global topology view covering the otherwise independent regional domains.

4

Inter-Domain Connectivity

BGP-LU provides labelled reachability between the independent SR-MPLS domains.

5

Constraint-Based Path Computation

CSPF or SAMCRA evaluates the global topology against the requested TE constraints.

6

Path Decomposition

The selected end-to-end path is decomposed into native SR-MPLS segments and BGP-LU inter-domain transitions.

7

PCEP Programming

The resulting forwarding instructions can be delivered to the ingress PCC through PCEP.

Global Path Decomposition

A global path cannot simply be interpreted as one continuous SR-MPLS SID stack because the regional SR domains are independent.

Native Domain

Native intra-domain links are represented using SR-MPLS forwarding information.

Domain Boundary

Inter-domain transitions are represented using the BGP-LU label associated with the selected WAN path.

Next Domain

Forwarding continues according to the receiving domain's own SR-MPLS and labelled forwarding state.

The synthetic inter-domain links in the global TED are not fake SR Adj-SIDs. They represent BGP-LU transitions between independent routing domains.

What the Lab Demonstrated

Global TE View

Multiple isolated SR-MPLS domains can be represented within a centralized global traffic-engineering topology.

Constraint-Based Routing

Global path computation can evaluate multiple regional domains and select an indirect transit path when required by the configured constraints.

Domain Independence

Regional IGP domains do not need to be merged in order for the controller to perform global path computation.

PCEP

The calculated forwarding plan can be translated into a controller-provisioned SR-MPLS LSP.

Important Architectural Finding

Topology visibility and forwarding reachability are different problems.

BGP-LS can provide the controller with topology and SID information from multiple domains, but this does not automatically create globally meaningful SR-MPLS SID forwarding across those independent IGP domains.

In the current design, BGP-LU therefore remains important at domain boundaries because it provides the labelled forwarding reachability required to cross between the independent SR-MPLS domains.

Current Limitation

Independent SR-MPLS domains do not automatically provide global remote Node-SID forwarding semantics. 

Desired conceptual model:

SR SID
   ↓
Remote SR SID
   ↓
Remote SR SID


Current multi-domain forwarding reality:

SR SID
   ↓
BGP-LU Label
   ↓
Remote Domain Forwarding

The experiment therefore uses the controller to compute the global TE path while respecting the actual forwarding mechanisms available at each domain boundary.

Future Direction

One possible next step is a lightweight multi-domain SR controller capable of separating global path computation from the forwarding implementation used inside each region.

Global TED

Collect topology and SR information using BGP-LS.

TE Engine

Perform SPF, CSPF and multi-constraint path computation.

Segment Compiler

Translate the global path into domain-specific forwarding instructions.

Southbound Programming

Program network devices through PCEP, NETCONF or gNMI.

Conclusion

This lab transformed multiple isolated SR-MPLS domains into a single traffic-engineering view.

An end-to-end constrained path was computed across the regional domains, translated into domain-specific SR-MPLS and BGP-LU forwarding instructions, programmed through PCEP, and validated in the data plane.
